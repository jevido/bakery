# Glossary

The ubiquitous language. These are the words used in conversation, in issues,
in the docs **and in the code**: class, type, function, table and event names
follow this list. If a term is missing or wrong, fix it here first, then in the
code.

A term that means different things in different contexts gets one row per
context. Terms used only inside one context can also live in that context's
document; list them here when people outside the context use them too.

| Term | Context | Meaning | Not to be confused with |
| ---- | ------- | ------- | ----------------------- |
| Member | identity | A person who may sign in to this installation of The Bakery, with a name, an email and a password hash. What they may do comes from their Membership in each Guild. | User, account |
| Guild | guilds | A group of Members that owns Projects (and through them Environments, Applications, Databases and Services), Servers (all but the Local server), S3 storages, Notification channels, Known hosts, API tokens, Goals and Issues. Everything it owns is invisible from every other Guild. Coolify's Team, Paperclip's Company. | team, company, organisation |
| Membership | guilds | A Member's place in a Guild, holding any number of Roles and always the Base role. A Member has at most one per Guild, and is in a Guild only through one. The Member's Permissions in the Guild are the union of their Roles' Permissions. An Agent's place in a Guild is its Agent membership. | Member, Agent membership |
| Agent membership | guilds | The Membership of an Agent in its Guild. It holds Roles like any Membership, and always the Base role, each Role below its Hirer's highest Role. It never makes the Agent a Member: it is never listed on the Members page, never receives Invitations or Transfer offers and is never the Guild Master. It goes when the Agent is terminated. | Membership, Member |
| Instance admin | identity | The Member Setup creates (formerly the Owner). Exactly one; acts with every Permission in every Guild, just below that Guild's Guild Master, sees every Guild, and can be neither demoted nor removed. Paperclip's `instance_admin`. Not a Guild's Guild Master. | Guild Master, Admin (a Role in one Guild), Owner |
| Current guild | guilds | The Guild a request acts in: for a Session the Guild named by the `bakery_guild` cookie, for an API token the Guild it was made in, for a Desktop key the Guild named by the request header `Bakery-Guild` (the Guild's id; the person's first Guild when it is absent). | Guild switcher |
| Role | guilds | A named set of Permissions in one Guild, with a color and a Position. A Membership holds any number of Roles. Seeded in every Guild: `Admin` (Administrator), `Member` (View resources, See secrets, Deploy, Manage applications, Manage work) and `Viewer` (View resources), which keep the meaning of the former `admin`, `member` and `viewer`. There is no `owner` Role. Discord's role. | team role (Coolify), membership role (Paperclip), rank |
| Base role | guilds | The Role every Member of a Guild holds, shown as `@everyone`, at Position 0. It cannot be assigned, removed, renamed or deleted; only its Permissions change. Seeded with none. Discord's `@everyone`. | Viewer |
| Position | guilds | A Role's place in its Guild's order; a higher Position is above. A Member's highest Role is the one with the highest Position they hold. Changed by dragging the Roles into a new order. | Rank, priority |
| Permission | guilds | One of a fixed list, by its wire key: `administrator` (every Permission; ignores Permission overrides), `view_resources` (read the Guild's Projects and everything in them, Servers, S3 storages and Notification channels, without Secrets), `see_secrets`, `deploy` (deploy, restart, stop, start, cancel, roll back), `manage_applications` (create, change and delete Projects, Environments, Applications, Databases, Scheduled backups, Services, their variables and routing settings), `manage_servers` (Servers, S3 storages, Known hosts), `manage_notifications` (Notification channels), `manage_guild` (the Guild's name, description and Issue prefix), `manage_members` (Invitations, removing Members, resetting their Two-factor authentication), `manage_roles` (Roles below one's own and Permission overrides), `hire_agents` (Hire Agents, and edit, Pause, Resume, Terminate and give or take Roles from the Agents one hired or whose Hirer ranks below one), `approve` (make Decisions on Approvals and Request revision), `manage_budgets`, `manage_work` (create and change Goals, Issues, Blockers and Issue documents, comment on Issues, request Approvals and comment on them). Deleting a Guild needs `administrator`. Every check asks for a Permission, never a Role. | Token permission, Role |
| Guild Master | guilds | The one Member of a Guild above every Role, with every Permission, who cannot be removed, re-roled or locked out by any Role or Permission override, and who cannot leave the Guild or delete their account while they are it. Changes only by an accepted Transfer offer. Whoever creates a Guild is its Guild Master. Discord's server owner. | Instance admin, Admin, Owner |
| Transfer offer | guilds | The Guild Master's offer to make one other Member of the Guild (never an agent) the Guild Master. Changes nothing until that Member accepts it; the Guild Master can withdraw it, the Member can decline it, and it expires 7 days after it was made. At most one is open per Guild. Accepting swaps the two in one step, and both keep their other Roles. | Invitation |
| Permission override | guilds | On one Project, per Role or per Member, one Permission set to allow, deny or inherit. Only `view_resources`, `see_secrets`, `deploy` and `manage_applications` can be overridden. The Base role's override applies first; then, over the other Roles, deny beats allow; an override for the Member beats both. A Project one may not view answers as if it did not exist. `administrator` and the Guild Master ignore them. Discord's channel overrides. | Token permission |
| Issue prefix | guilds | 1 to 5 capital letters on a Guild (Paperclip's `issue_prefix`), unique in the installation. Derived from the Guild's name when it is created: its first 3 letters A–Z, uppercased, `GLD` when it has none, then `A`, `B`, … `Z`, `AA`, … appended until unique. Changeable on the Guild's General page; renaming the Guild keeps it. The installation's first Guild, Default, has `DEF`. | Issue identifier |
| Owner | identity | Retired: the Member Setup created before Guilds, with the `owner` Role. That Member is now the Instance admin. | Instance admin, Admin |
| Setup | identity | The one-time step that creates the Instance admin and the first Guild. Refused once an Instance admin exists. | Install |
| Invitation | guilds | An email and the Roles it brings, for one Guild, made by a Member with `manage_members`, with a link that is good once and for 7 days, until revoked or declined. Accepting it creates the Member when the email is new, or else adds a Membership to the Member who has it. | Notification, Transfer offer |
| Session | identity | Proof that a Member signed in: a JWT carried in the `bakery_session` cookie. It stops counting when the Member changes their password or signs out everywhere else. | API token |
| Profile | identity | A Member's own name, password, Sessions and Two-factor authentication, changed only by that Member on their Profile page. | Member (as others see them) |
| Two-factor authentication | identity | A TOTP secret on a Member. When it is on, signing in needs an Authenticator code or a Recovery code after the password. | Deploy key, API token |
| Authenticator code | identity | The 6 digits the Member's authenticator app shows (RFC 6238, 30 second steps). Accepted for the current step or one either side, and only once. | Recovery code |
| Recovery code | identity | One of 10 single-use codes handed out when Two-factor authentication is switched on, for signing in without the phone. Stored hashed. | Authenticator code, API token |
| Login challenge | identity | The 5 minutes between a correct password and the second sign-in step of a Member with Two-factor authentication; at most 5 wrong codes. | Session |
| API token | identity | A named secret (`bky_…`) of one Member, made in one Guild and working only there, sent as `Authorization: Bearer`, with its Token permissions and an optional expiry, acting with at most that Member's current Permissions in that Guild. Shown once, stored hashed, revocable; refused once expired; it dies with its Member. | Session, Deploy key |
| Token permission | identity | One of `root`, `write`, `deploy`, `read`, `read:sensitive` on an API token, capping what the token may do with its Member's Permissions in its Guild: `root` allows everything those Permissions do; `write` allows changes other than deploy actions; `deploy` allows deploying, restarting, stopping, starting, cancelling and rolling back; `read` allows reading without Secrets; `read:sensitive` allows reading Secrets as well. Coolify's "abilities"; the dashboard and the wire keep the word `permissions` for them. | Permission (of a Role), ability, scope |
| Desktop app | identity | The Bakery's app a person installs on their own machine and connects to one or more Bakeries. Its Runner runs that person's Agents with their own `claude` login; it holds no domain data beyond a cache and the local checkouts, and talks to a Bakery only through its API. | Desktop (the server's record of one copy), dashboard |
| Desktop | identity | One signed-in copy of the Desktop app as the server knows it: its person (one Member), a name such as the machine's hostname, when it was created, when it was last seen, and when it was signed out. Made by approving a Desktop sign-in. | Desktop app, Session |
| Desktop sign-in | identity | A short-lived request a Desktop app makes to be approved by a signed-in person in the browser (Paperclip's CLI auth challenge): `pending`, then `approved` (once), `cancelled`, or `expired` 10 minutes after it was made. | Login challenge |
| Desktop key | identity | The bearer secret a Desktop authenticates with (`bky_desk_…`), minted by the Desktop app with its Desktop sign-in and stored only as its hash. It acts as its person, with their own Permissions, in any of their Guilds, chosen per request by `Bakery-Guild`. It stops counting when its Desktop is signed out or 30 days after it was last used. | API token, Session |
| Run key | agents, identity | The bearer secret (`bky_run_` + 48 hex characters) a Desktop receives once, in the answer to its claim of a Run, and hands to that Run's `claude`. Stored only as its SHA-256 on the Run; it counts only while that Run is `running`, and stops the moment the Run ends. Paperclip's run JWT. | Desktop key, API token |
| Agent principal | identity | Who a request made with a Run key acts as: the Run's Agent, in the Run's Guild, during that Run. Never a Member and never the Hirer; it does only what the Agent membership's Permissions allow, and only on routes open to Agents. | Member, Hirer, Agent actor |
| Secret | identity (used by every context) | A value a viewer may not read: Environment variable and Shared variable values, Database credentials and URLs, Service variable values, the Webhook secret, the Git host token, Backup execution contents. | Environment variable |
| Project | projects | A named group of Environments, usually one product. Belongs to one Guild. | Repository |
| Environment | projects | A stage inside a Project (`production` is created with every Project; more can be added). Holds its Resources. | Environment variable, the dev/next/prod environments of this repo |
| Application | projects | Something The Bakery builds from a Git repository (or pulls as a Docker image) and runs as one Container behind its Domains. | Service, Container |
| Resource | projects (used by every context) | An Application, Database or Service in an Environment; Coolify's word for all three, as in an Environment's list of Resources. | Resource limits |
| Slug | projects | The URL-safe, unique short name of an Application, used in its default Domain and image name. | Name |
| Git repository | projects | Where an Application's code comes from, for every Build pack except `dockerimage`: a git URL and its *Git branch*. Either a public `https://` URL, or an SSH URL (`ssh://git@host/path` or `git@host:path`) that always has a Deploy key. The Application tab that edits it is labelled "Source", as in Coolify; otherwise *Source* is kept for a GitHub App or GitLab connection, which The Bakery does not have yet. | Repository on disk, Source |
| Deploy key | projects | The SSH key pair The Bakery generates for one Application. A member adds the public half to the repository as a read-only deploy key; the private half is encrypted at rest. | Private key, API token |
| Build pack | projects | How an Application becomes an Image: `dockerfile` (build the Dockerfile at a path in the Git repository), `nixpacks` (Nixpacks detects the language and writes the Dockerfile), `static` (serve the Publish directory of the Git repository as files on port 80), or `dockerimage` (pull a Docker image from a registry; no Git repository). | Buildpacks (Heroku/CNB) |
| Docker image | projects | The registry reference a `dockerimage` Application runs, always with its registry host, e.g. `docker.io/traefik/whoami:v1.10`. | Image (the Deployment's own tag) |
| Registry credentials | projects | The username and password or token a `dockerimage` Application pulls its Docker image with. The password is encrypted at rest and never shown. | Deploy key |
| Publish directory | projects | The directory of the Git repository a `static` Application serves, relative to the repository root; `.` by default. | Dockerfile path |
| Environment variable | projects | A name and value of one Application, handed to its build, its Container or both (see Variable scope). The value is encrypted at rest. | Environment |
| Variable scope | projects | Where a variable reaches: *build* (a build arg of the Image) and/or *runtime* (the Container's environment). Runtime only by default. | Environment |
| Shared variable | projects | A variable set on a Project or an Environment and inherited by every Application in it. An Application's own Environment variable wins over its Environment's, which wins over its Project's. | Environment variable |
| Healthcheck | projects, deployments | An HTTP path probed inside a new Container until it answers 2xx or 3xx, with an interval, a timeout, a number of retries and a start period. Off by default. The Route only moves to a Container that passed it. | Container state |
| Domain | projects, routing, services | One of the hostnames an Application or a Public Component is reached on. An Application has 1 to 10; the first is its *primary* Domain (shown in lists, used for links). Each is unique across The Bakery (Applications and Services share one namespace), and never the dashboard domain. The default is one Domain `<slug>.<domain suffix>` (`localhost` in development). | URL |
| Persistent storage | projects, deployments | A named volume of one Application (`bakery-app-<application-id>-<name>`), mounted at its mount path in every Container of that Application, so what is written there survives redeploys and rollbacks. | Bind mount (later), Image |
| Resource limits | projects, deployments, databases | The memory (MB) and CPU (cores) each Container of an Application, or the Container of a Database, may use. Empty means unlimited. Applied from an Application's next Deployment, and to a Database at once (its Container is recreated). | Server capacity |
| Deployment | deployments | One attempt to turn an Application's Git repository (or Docker image) into its running Container. | Release, build |
| Deploy trigger | deployments | What started a Deployment: `manual` (a member pressed Deploy), `webhook` (a push), `rollback` (a member rolled back to an earlier Deployment) or `restart` (a member restarted the Application). | Build pack |
| Deployment status | deployments | Where a Deployment is: `queued`, `cloning`, `building`, `starting`, then `finished`, `failed` or `cancelled`. A `dockerimage` Deployment skips `cloning` and pulls during `building`. The first four are *active*; `cloning`, `building` and `starting` are *running*. | Container state |
| Cancel | deployments | A member ending an active Deployment before it finishes. It ends `cancelled`, what it made is removed, and the running version stays. | Fail, rollback |
| Rollback | deployments | A Deployment that starts an earlier finished Deployment's Image again, without cloning or building. | Revert (git), redeploy |
| Restart | deployments | A Deployment that starts the Image of the Application's newest finished Deployment again with today's settings, without cloning or building, as Coolify's Restart does. | Rollback, Redeploy |
| Redeploy | deployments | Deploy of an Application that is already running; with *without cache* (Coolify's `force_rebuild`) every layer of the Image is built again. | Restart |
| Stop | deployments | Taking the Application's Route out of its Proxy and stopping and removing its own Containers; its Previews keep running. It stays stopped until the next Deploy, Restart or Rollback. | Cancel, Delete |
| Application status | deployments | Coolify's status of an Application, read from its own Containers: `running:healthy`, `running:unhealthy` (its Healthcheck fails now), `running:unknown` (it has no Healthcheck), `restarting`, `degraded:unhealthy` (some of its Containers run, others stopped) or `exited` (none run). | Deployment status, Server status |
| Deployment log | deployments | The ordered lines a Deployment wrote: its own `info` lines and the `out`/`err` output of git and the build. | Container logs |
| Container logs | deployments, databases, services | What a running Application's, Database's or Component's Container writes to stdout and stderr. | Deployment log |
| Image | deployments | The result of a Deployment, built or pulled and re-tagged as `localhost/bakery/<slug>:<deployment-id>`. | Container |
| Source image | deployments | The reference with digest a `dockerimage` Deployment pulled, e.g. `docker.io/traefik/whoami@sha256:…`. Shown where git Deployments show their commit. | Docker image |
| Container | deployments, services | A running instance of an Image, named `bakery-app-<application-id>-<deployment-id>` for an Application and `bakery-svc-<service-id>-<component>` for a Component. | Application |
| Webhook | deployments | The URL and secret a git host calls on every push, so a push to an Application's branch deploys it. | Notification webhook (later) |
| Pull request | deployments | A request on a git host to merge a branch into the Application's branch; a GitLab merge request counts as one. Known to The Bakery only through Webhook calls. | Deployment |
| Previews | deployments | The switch on an Application's Webhook that lets Pull requests start Previews. Off until switched on. | Preview |
| Preview | deployments | A running copy of an Application built from the head branch of one open Pull request in the Application's own repository, with its own Containers, Volumes and Preview route. `open` until the Pull request closes, then `closed` with nothing left running. | Environment, Rollback |
| Preview number | deployments | The Pull request's number (GitLab: its `iid`); names the Preview, its Containers, Volumes and Preview domain. | Deployment id |
| Preview domain | deployments, routing | `pr-<number>.<primary Domain>`, where a Preview is served. | Domain |
| Preview route | routing | Where a Preview's Preview domain is served from: one per Application and Preview number, on the Application's Server, with the Application's headers and basic auth. | Route |
| Preview comment | deployments | The one comment The Bakery keeps on a Pull request, edited after every Preview Deployment and when the Preview is removed. Needs a Git host token. | Notification |
| Git host token | deployments | An access token for the git host, stored encrypted on the Webhook, that lets The Bakery write the Preview comment. A Secret. | Deploy key, API token |
| Auto-deploy | deployments | Whether a verified push to the Application's branch queues a Deployment. On by default. | Redeploy |
| Known host | deployments | A git host's SSH host key, remembered per Guild on the first clone from that host and required to match on every later clone in that Guild. | Host key (Servers) |
| Server | servers | A machine The Bakery runs Containers on: the Local server, through the rootless Podman socket, or a Remote server over SSH, which belongs to one Guild. It has a name and an optional description (free text, at most 255 characters). Applications run on their Target server; Databases and Services still run on the Local server. | Proxy |
| Target server | projects, deployments, routing | The Server an Application's Images are built on and its Containers run on. Chosen when the Application is added and fixed afterwards; the Local server when none was chosen. | Server connection |
| Server connection | servers | A pooled way for other contexts to reach one Server: its Podman API and any unix socket on it. One SSH connection per Remote server, redialled when it drops. | Validation |
| Local server | servers | The Server The Bakery itself runs on (named `localhost` until renamed). Always exists; only its name and description can be edited, only by the Instance admin, and it cannot be deleted. It belongs to no Guild, and every Guild deploys to it. | Remote server |
| Remote server | servers | A Server reached over SSH as a given user, its rootless Podman socket tunnelled through that connection. | Local server |
| Private key | servers | The SSH key pair The Bakery generates for one Remote server. An admin adds the public half to the user's `authorized_keys`; the private half is encrypted at rest. | Deploy key |
| Host key | servers | A Remote server's SSH host key, pinned on the first connection and required to match on every later one until an admin forgets it. | Known host (git hosts) |
| Validation | servers | The checks run against a Server (`ssh`, `podman`, `socket`, `linger`, `ports`) and their outcome; it sets the Server status, as does the Server probe. | Healthcheck, Server probe |
| Server status | servers | `unvalidated`, `reachable` (every required check passed) or `unreachable`. | Container state |
| Server metrics | servers | CPU, memory and disk use of a Server, read live from Podman. | Container metrics |
| Server details | servers | The operating system, architecture, kernel, CPU cores, memory, Podman version and boot time of a Server, read live from Podman. | Server metrics |
| Container metrics | servers | CPU and memory use of each Bakery Container on a Server, read live. | Server metrics, Container logs |
| Server probe | servers | The check every 5 minutes of every Server whose latest Validation passed: can The Bakery reach it, and how full is its disk. Two failed probes in a row make a Reachable Server Unreachable, one good probe makes it Reachable again; *high disk usage* is raised at 90 % used and cleared below 85 %. Only a change is announced. | Healthcheck, Validation |
| Cleanup | servers | Freeing a Server's disk: dangling Bakery images and build layers, plus Image retention for the Applications that run on it. Daily and on demand. | Delete |
| Image retention | deployments | Per Application, the Images of the running Deployment and of the last five finished Deployments are kept; older ones are removed during Cleanup, and a Rollback to one of those is refused ("the image is gone"). | Cleanup |
| Service | services | Multi-container software described by a Compose file and run in an Environment, created from a Service template or a pasted Compose file. | Application, a compose `services:` entry (that is a Component), the repo's `services/` directory |
| Compose file | services | The `compose.yml` text a Service is made of, in the subset The Bakery supports; anything else is refused with its line. | Containerfile |
| Component | services | One entry under a Compose file's `services:`, run as one Container `bakery-svc-<service-id>-<name>`. *Public* when it has a port and Domains. | Service, Application |
| Service variable | services | A `${NAME}` a Compose file refers to, with a value stored encrypted: set by a member, or generated when it is a Magic variable. | Environment variable, Shared variable |
| Magic variable | services | A Service variable The Bakery fills in, named as in Coolify's templates: `SERVICE_PASSWORD_*`, `SERVICE_USER_*`, `SERVICE_BASE64_*` (generated once), `SERVICE_FQDN_<NAME>` / `SERVICE_URL_<NAME>` (the Component's primary Domain). A `_<PORT>` suffix makes the Component public on that port. | Database credentials |
| Service template | services | A named, described Compose file embedded in The Bakery, with a category and a logo; the Services catalog on the New Resource page. | Build pack |
| Service status | services | `running`, `stopped`, `deploying`, `degraded` or `failed`, summed up from each Component's status (read from Podman like a Database status). Only the desired state is stored. | Deployment status |
| Service route | routing | A Public Component's Domains pointed at its Container and port. One per Public Component, rendered with the Routes. | Route |
| Proxy | routing | The Caddy container `bakery-proxy` on a Server, configured only through its admin API. One per Server that has Routes; the Local server's also serves the Dashboard Route and Service routes. | Server |
| Route | routing | An Application's Domains pointed at one Container and port on its Target server, served by that Server's Proxy. One per Application. | Endpoint |
| Route settings | routing | How the Proxy treats one Application's traffic: its Redirect, Response headers and Basic auth. Applied at once, without a Deployment. | Application settings in projects |
| Redirect | routing | `both` ("Allow www & non-www", the default: no redirect), `non-www` ("Redirect to non-www") or `www` ("Redirect to www"): with `non-www` or `www`, for every Domain the counterpart with `www.` removed or added answers with a permanent (308) redirect to the chosen form, keeping path and query. | Domain |
| Response header | routing | A header name and value the Proxy sets on every response of an Application. | Environment variable |
| Basic auth | routing | One username and password the Proxy asks for before any request reaches the Application. Only a bcrypt hash of the password is kept. | Session |
| Dashboard Route | routing | The Route to The Bakery's own dashboard and API on the configured dashboard domain: `/api/*` to the API, the rest to the dashboard. Derived from configuration, never stored. | Route |
| Database | databases | A data store of one Database type that The Bakery runs as one Container (`bakery-db-<slug>`) in an Environment, with its data in one volume. Created in one step; never built or deployed. | Application, Postgres (The Bakery's own database) |
| Database type | databases | What kind of Database it is: `postgresql`, `mysql`, `mariadb`, `redis`, `valkey` or `mongodb`. Fixed once the Database exists. | Build pack |
| Database version | databases | The image tag of the Database type a Database runs, e.g. `18-alpine`. Each Database type has a default. | Deployment |
| Image (of a Database) | databases | Coolify's Image field: the Database type's Docker Hub repository and the Database version, e.g. `postgres:18-alpine`. Only the tag can change; the repository is the Database type's. | Database type |
| Database credentials | databases | The username (`bakery`), password (and for MySQL/MariaDB a root password) and database name (the Slug with `_` for `-`) of a Database. Generated by The Bakery, encrypted at rest, shown to members and admins (a Secret). | Registry credentials |
| Internal URL | databases | The connection URL of a Database on the `bakery` network, with host `bakery-db-<slug>`. What Applications use. | Public URL, Domain |
| Public port | databases | A host port (1024–65535, unique among Databases) a Database is published on, so it can be reached from outside the Server. None by default. | Port (of an Application) |
| Public URL | databases | The connection URL of a Database through its Public port on the Server's public host. Only exists with a Public port. | Internal URL, Domain |
| Database status | databases | What a Database's Container is doing, read from Podman: `starting` (running, not answering yet), `running` (answers its Database type's readiness probe), `stopped` (a member stopped it), `exited` (stopped on its own) or `missing` (no Container). Not stored; a member's wish (running or stopped) is its *desired state*. | Deployment status |
| Backup execution | databases | One logical dump of a Database, made for one of its Scheduled backups, written to the Backups directory and, when that Scheduled backup names an S3 storage, uploaded there. Its *status* is `running`, `succeeded` or `failed` (with a reason); its *trigger* is `manual` (Back up now) or `scheduled`. Only PostgreSQL, MySQL, MariaDB and MongoDB have Backup executions. | Snapshot, volume copy |
| Scheduled backup | databases | When a Database is backed up by itself: on or off, a five-field cron expression in UTC, a Retention and optionally an S3 storage, with its own Backup executions. A Database has any number; a new one starts with one, off, daily at 03:00 UTC. | Scheduled command |
| Retention | databases | How many of a Scheduled backup's newest succeeded Backup executions are kept (1–100, default 7); older ones are deleted from the Backups directory and the S3 storage alike. | Expiry |
| Backups directory | databases | The directory on the Server The Bakery writes Backup execution files to, `<database id>/<UTC timestamp>.<ext>` below it. The volume `bakery-backups` on a server. | Persistent storage |
| S3 storage | databases | An S3-compatible bucket Backup executions are uploaded to: endpoint, region, bucket, optional prefix, access key and secret key. The secret key is encrypted at rest and never shown. Belongs to one Guild. | Persistent storage, Backups directory |
| Restore | databases | Replacing the data of a running Database with the contents of one of its succeeded Backup executions, from the Backups directory or, when the file is gone, from its S3 storage. Anything written since the Backup execution is lost. | Rollback |
| Notification channel | notifications | A named place Notifications go to: a Channel kind, its settings (secrets encrypted, never shown), the Event kinds it is subscribed to, and whether it is enabled or disabled. A disabled one gets no Notifications. Belongs to one Guild and gets only Notifications about what that Guild owns; managed by its admins. | Webhook (inbound, deployments) |
| Channel kind | notifications | `email`, `discord`, `telegram`, `slack`, `pushover`, `webhook` or `ntfy`: how a Notification channel is reached. | Event kind |
| Event kind | notifications | What a Notification is about, named as in Coolify: `deployment_failure`, `deployment_success`, `backup_failure`, `backup_success`, `server_unreachable`, `server_reachable`, `server_disk_usage`. | Domain event |
| Notification | notifications | A message about one thing that happened: Event kind, title, body, a link into the dashboard. Sent to every Notification channel of the Guild it concerns that is subscribed to its Event kind. | Invitation, log line |
| Delivery | notifications | One Notification sent to one Notification channel: `pending`, `sent` or `failed`, with up to 3 attempts and the last error. The 50 newest per channel are kept. | Deployment |
| Board | work | The human Members of a Guild, as Paperclip calls them when it sets them against agents. | board of directors |
| Goal | work | An outcome a Guild works toward: a title, a Markdown description, a Goal level, a Goal status, an optional parent Goal (Goals form a tree within one Guild) and an optional owner Member. | the goals of this repository's planning |
| Goal level | work | `guild`, `agent` or `task`; default `task`. Paperclip's `company`, `agent` and `task`; its `team` is left out because Team is Coolify's word for a Guild. | Position |
| Goal status | work | `planned`, `active`, `achieved` or `cancelled`; default `planned`. | Issue status |

| Blocker | work | An Issue another Issue waits on, in the same Guild. An Issue is *blocked by* its Blockers and *blocking* the Issues that wait on it. Blockers never change an Issue status: `blocked` is a status a person sets. | parent Issue, Issue status `blocked` |

| Restore (a Revision) | work | Save an older Revision's title and body as the new newest Revision of its Issue document. | Rollback (of a Deployment) |

| Activity event | work | One entry in the Activity: an Actor did an Action to one Goal, Issue, Approval or Agent at one time, with what changed. Never edited and never deleted on its own; it goes only with its Guild. | Deployment log, notification |

| Actor | work | The Member (Paperclip's `actorType: "user"`) or the Agent actor (`actorType: "agent"`) who did what an Activity event records. What a person does to an Agent has that person as its Actor; what an Agent does with its Run key has the Agent. | Assignee, author |
| Inbox | work | A Member's own list, in one Guild, of the Issues they are Touched by, showing which are Unread. Paperclip's Inbox. | notifications, Notification channel |

| Last touch | work | The latest of a Member's last Comment on an Issue, their Read mark on it, the Issue's creation if they created it, and the Issue's last change (a Comment is not one) if they are its Assignee. | Read mark |
| Unread | work | Said of a Touched Issue with a Comment, not deleted, by another Member written after the Member's Last touch. | new, unseen |
| Read mark | work | When a Member last read an Issue: set when they open it or mark it read, removed when they mark it unread. | Activity event, seen |
| Inbox archive | work | A Member taking a Touched Issue out of their Mine tab; it stays in Recent. Paperclip's "archive" in the Inbox. | deleting or cancelling the Issue |
| Resurface | work | An archived Issue coming back to Mine by itself once, after the Inbox archive, another Member writes a Comment on it or its Issue status moves to `in_review`, `blocked` or `done` (not `done` if it was already completed when archived). | Inbox archive |
| Approval | work | A Member's request that the Board decide on something: one Approval type, a payload (what is asked) and one Approval status. It belongs to one Guild and may have Linked issues. Paperclip's approval. | Review, sign-off, confirmation |
| Approval type | work | What an Approval asks, by its wire key. `request_board_approval`: a decision asked in words, with a title, a summary, a recommended action, what happens on approval and a list of risks. `hire_agent`: whether to Hire an Agent; its payload is the Agent's id, name, Job, Title, icon, Manager, Capabilities and Role names, and it is created only by Hire, never through `POST /api/approvals`. | Approval status | work | `pending`, `revision_requested`, `approved`, `rejected` or `cancelled`. `cancelled` is Paperclip's word and meaning: a `hire_agent` Approval whose Agent was terminated before a Decision; it is not Actionable and never changes again. | Issue status, Agent status |
| Actionable | work | Said of an Approval in `pending` or `revision_requested`: only an Actionable Approval can get a Decision. | open, active |
| Requester | work | The Member who asked for an Approval; none once their account is gone. | creator, author |
| Decision | work | Approve or reject, made on an Actionable Approval by a Member with `approve`. It records who decided, when, and an optional Decision note. | Resolution, verdict |
| Decision note | work | The optional words a Member with `approve` adds to a Decision or a Request revision. | Comment, Approval comment |
| Request revision | work | A Member with `approve` sending a `pending` Approval (never a `hire_agent` one) back to its Requester; its Approval status becomes `revision_requested`. | Reject |
| Resubmit | work | The Requester putting a `revision_requested` Approval back to `pending`, optionally with a changed payload; the earlier Decision note and decider are cleared. | Request (a new Approval) |
| Approval comment | work | A Markdown message by a Member on one Approval. Never edited or deleted. | Comment, Decision note |
| Linked issue | work | An Issue an Approval is about, in the same Guild. An Approval may have several, and an Issue several Approvals. | Blocker, Sub-issue |
| Agent | agents | An AI worker hired into one Guild. | Job | agents | What an Agent does in the Org chart, one of: `ceo` CEO, `cto` CTO, `cmo` CMO, `cfo` CFO, `security` Security, `engineer` Engineer, `designer` Designer, `pm` PM, `qa` QA, `devops` DevOps, `researcher` Researcher, `general` General (the default). | Run status | agents | `queued` (waiting for a Desktop of the Hirer), `running` (claimed by one), `succeeded`, `failed`, `cancelled` (by a person, or by Pause or Terminate) or `lost` (its Desktop stopped reporting before its Lease ran out; a new `queued` Run takes its place).
