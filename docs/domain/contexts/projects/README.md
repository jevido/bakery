# projects

- Subdomain: supporting
- Hosted in: `services/api` (module `contexts/projects`)

## Purpose

Holds what the Owner wants to run: Projects, their Environments, the
Applications in them, each Application's Environment variables, Healthcheck, Domains, Persistent storage and Resource limits, and the
Shared variables of Projects and Environments. It is **not**
responsible for building or running anything (deployments) or for how traffic
reaches an Application (routing).

## Language

| Term | Meaning |
| ---- | ------- |
| Project | A named group of Environments. |
| Environment | A stage in a Project; `production` exists from the start and people add, rename and delete more. Names are unique per Project, case-insensitively. |
| Application | A Build pack with what it needs (Git repository and Dockerfile path, Git repository and Publish directory, or Docker image and Registry credentials) + port + Domains, plus Environment variables, a Healthcheck, Persistent storage and Resource limits. |
| Build pack | `dockerfile`, `nixpacks`, `static` or `dockerimage`: how the Application becomes an Image. |
| Docker image | The full registry reference a `dockerimage` Application runs. |
| Registry credentials | Username and password/token a `dockerimage` Application pulls with. |
| Publish directory | The directory of the Git repository a `static` Application serves. |
| Variable scope | Build (a build arg) and/or runtime (the Container's environment). |
| Shared variable | A variable on a Project or Environment, inherited by its Applications. |
| Healthcheck | Whether and how a new Container is probed before it takes traffic: path, interval, timeout, retries, start period. |
| Deploy key | The SSH key pair of one Application with an SSH Git repository. |
| Domain | One of the 1–10 hostnames of an Application; the first is its primary Domain. |
| Persistent storage | A name and a mount path; every Container of the Application mounts the volume of that name there. |
| Resource limits | Memory in MB and CPU in cores per Container; empty means unlimited. |
| Target server | The Server the Application is built and runs on. Chosen when it is added, fixed afterwards; none chosen means the Local server. |
| Application snapshot | The read-only view of an Application handed to deployments, with its variables merged and decrypted into a build and a runtime set, and the Deploy key's private half decrypted. |

## Model

### Aggregates

| Aggregate | Invariants |
| --------- | ---------- |
| Project | Name is not empty. Is created together with its `production` Environment, in one transaction. An Environment's name is 3–255 characters of letters, digits, spaces and `- _ . / @ & ( ) # , : +` (Coolify's name rule) and unique within the Project, case-insensitively; its description is at most 255 characters. An Environment with any Application, Database or Service in it cannot be deleted; the last Environment of a Project may be, as in Coolify, leaving the Project empty. Its Shared variables, and those of each of its Environments, follow the Environment variable rules below. |
| Application | Always has a name, at most 100 characters; one created without a name gets a generated one, as Coolify names it: `docker-image-<random>` for a Docker image, otherwise the kebab case of `<repository>:<branch>-<random>` (the last path segment of the Git repository without `.git`, cut to fit), where `<random>` is 8 lowercase letters and digits. Slug is unique across The Bakery, lowercase `[a-z0-9-]`. The Build pack is `dockerfile` (default), `nixpacks`, `static` or `dockerimage`. A `dockerimage` Application has a Docker image that names its registry host (no short names like `nginx`, at most 500 characters, no spaces), and no Git repository, Dockerfile path or Deploy key; it may have Registry credentials, username and password both set or both empty, the password encrypted at rest and never returned. Every other Build pack has a Git repository and no Docker image or Registry credentials. A `static` Application has a Publish directory that is relative and does not contain `..`, and always listens on port 80. The Git repository URL is either `https://` without credentials, or an SSH URL (`ssh://user@host[:port]/path` or `user@host:path`); never `file://`, `ext::`, a local path or anything starting with `-`. An SSH Git repository always has a Deploy key (ed25519, generated by The Bakery); an `https://` one has none. The Deploy key's private half is encrypted at rest and only leaves the context in the snapshot; it is never shown or logged. The Git branch is not empty. Dockerfile path is relative and does not contain `..`. Port is 1–65535. It has 1 to 10 Domains, in order (the first is primary), each a lowercase hostname, unique across The Bakery (across every Application's Domains, and no Service's Domain as told by the registered Domain checks), not the dashboard domain (reserved for the Dashboard Route), listed once; an empty list becomes the one default Domain `<slug>.<domain suffix>`. At most 10 Persistent storages: names match `^[a-z0-9][a-z0-9-]{0,39}$` and are unique per Application; mount paths are absolute, already clean (`path.Clean` leaves them unchanged), not `/`, without `:` or `,`, at most 200 characters and unique per Application. Resource limits are optional: memory 16–65536 MB, CPU 0.1–64 cores with at most two decimals. Environment variable names match `^[A-Za-z_][A-Za-z0-9_]*$` and are unique per Application; values are encrypted at rest and never logged; each has at least one scope (build, runtime), runtime only by default. The Healthcheck is off by default; its path starts with `/`, interval is 1–300 s, timeout 1–60 s, retries 1–100, start period 0–600 s. The Target server is set only when the Application is created, must be a Server that exists then (asked through `servers.Exists`), and never changes; the Local server is stored as none, so it has one representation. |

### Commands

- `CreateProject`, `RenameProject`, `DeleteProject` (refused while it has Applications, or while a registered in-use check, such as databases', says the Project is in use).
- `CreateEnvironment(project, name, description)`, `UpdateEnvironment` (rename, describe), `DeleteEnvironment` (refused while it has Applications, or while a registered in-use check, such as databases' or services', says the Environment is in use; its Shared variables go with it).
- `CreateApplication(environment, ...)`, `UpdateApplication`, `DeleteApplication`.
- `ReplaceEnvironmentVariables(application, [name, value, build, runtime])`: the whole set is replaced at once.
- `ReplaceProjectSharedVariables(project, ...)`, `ReplaceEnvironmentSharedVariables(environment, ...)`: the same, for Shared variables.
- `RegenerateDeployKey(application)`: a new key pair replaces the old one; the Owner has to add the new public half to the repository.

### Domain events

- `ApplicationDeleted { applicationID }`: routing drops its Route and Route settings; deployments removes its Containers and volumes.
- `ApplicationDomainsChanged { applicationID, domains }`: fired after an update that changed the Domains (in their new order); routing points the Application's Route at them.

## Integration

- **Publishes:** `ApplicationForDeploy(id) (ApplicationSnapshot, error)` for
  deployments (Build pack, Git repository, Dockerfile path, Publish directory, Docker image and decrypted Registry credentials, port, Domains, Healthcheck, Persistent storages, Resource limits,
  `BuildVariables` and `RuntimeVariables`, Deploy key, and `ServerID`, the Target server, 0 for the Local server). The two variable sets are
  already merged (Application > Environment > Project) and split by scope.
  Changing its fields is a breaking change for deployments.
  `ApplicationExists(id)` for routing, which keeps Route settings per
  Application and refuses them for one that does not exist.
  `Environment(id)` (id, Project id, name), `OnProjectDeleting(check)` and
  `OnEnvironmentDeleting(check)` for databases and services, which place
  Databases and Services in Environments and refuse the deletion of a
  Project or an Environment that still has them.
  `DomainInUse(domain)` (an Application has it, or it is the dashboard
  domain) and `OnDomainCheck(check)` for services: Application Domains
  and Service Domains are one namespace, and each side asks the other
  before storing one.
- **Consumes:** the Owner's Session (identity middleware); `servers.Exists`
  when an Application is created with a Target server, and registers
  `servers.OnServerDeleting` so a Server that Applications target is not
  deleted.

## Why it's shaped this way

- **Environments exist from day one**, and every Project starts with
  `production`. Coolify's Project > Environment > Resource shape is what
  staging and other stages need, and adding a level under existing
  Applications later would have been a data migration. People add, rename
  and delete Environments as in Coolify's Project page and Environment
  settings.
- **The last Environment of a Project may be deleted**, as Coolify allows:
  the Project then shows its empty state and "New environment". Refusing it
  would be a rule Coolify does not have, for no data that would be lost.
- **The dashboard domain is reserved through configuration, not by asking
  routing.** Projects reads `BAKERY_DASHBOARD_DOMAIN` itself, so it needs no
  dependency on routing to refuse it; both contexts read the same setting.
- **Git repository URLs must be `https://`, `http://` or SSH.** `http://`
  is allowed as Coolify allows it, for a Git server without TLS (a Forgejo
  on the local network); the clone then allows only that protocol. The deployment worker clones whatever
  URL it is given where the API runs (on the host in development, in the
  API container on a server); a `file://` URL or a local path would let an
  Application read the host's files. Private repositories are reached over
  SSH with a Deploy key instead, and an SSH Git repository without a key cannot
  exist, so The Bakery never clones with a key of its own user.
- **Deploy keys first, a GitHub App later.** A deploy key works with every
  git host (GitHub, GitLab, Gitea, Forgejo) and needs nothing but the
  repository's settings page. A GitHub App needs a registration and a
  public callback, and becomes a Source of its own, Coolify's word for such a connection.
- **One Deploy key per Application**, not one per installation: GitHub refuses the
  same deploy key on a second repository, and a leaked key then opens only
  one repository.
- **Environment variable values are encrypted with the application key**
  (`APP_KEY`, AES via Goravel's Crypt). A database dump alone does not leak
  them. Cost: losing `APP_KEY` loses every value.
- **Shared variables are inherited, not referenced.** Coolify lets a value
  say `{{project.NAME}}`; The Bakery simply hands every Application its
  Environment's and Project's variables, with the Application's own winning
  over its Environment's and those over its Project's. That covers the usual
  case (one `DATABASE_URL` per Environment) without a template language;
  references can be added on top later. A name overridden at a lower level
  takes that level's scope too, so the Owner sees one row per name.
- **The merge happens here, not in deployments.** Deployments gets two plain
  sets (`BuildVariables`, `RuntimeVariables`) and never learns that Projects and
  Environments have variables, so how variables are shared can change
  without touching it.
- **Build values end up in the Image's history.** Build args are visible to
  anyone who can inspect the Image, so runtime is the default scope and the
  dashboard warns when a variable is marked build.
- **Registry credentials belong to the Application**, not to a list of
  registries. It is the smallest thing that lets a private image deploy, and
  a leaked credential reaches one Application's image. A shared list per
  registry can come with Teams, when several people manage credentials.
- **Docker images are stored with their registry.** On a server, rootless
  Podman resolves a short name like `nginx` through
  `unqualified-search-registries`, which differs per distribution and may
  prompt. Coolify takes short names as Docker does, so The Bakery accepts
  them too and stores them qualified the way Docker reads them (`nginx` is
  `docker.io/library/nginx`, `traefik/whoami` is `docker.io/traefik/whoami`);
  the stored reference means the same thing on every Server.
- **Nixpacks, not Railpack, for builds without a Dockerfile.** Railpack
  builds only through BuildKit (its plan is a BuildKit frontend), which
  Podman's builder (Buildah) cannot run, and running BuildKit would mean a
  second build daemon next to Podman. Nixpacks can write a plain Dockerfile
  that Podman builds. Nixpacks is in maintenance mode; if Railpack ever
  writes a Dockerfile it can replace it under the same Build pack name.
- **A static site has no build step yet** and always listens on port 80:
  the Publish directory is copied as is into a Caddy file server. A site
  that needs `npm run build` uses Nixpacks or a Dockerfile.
- **The Healthcheck belongs to the Application**, since it describes the
  app (what path says it is ready), and deployments reads it from the
  snapshot like the port.
- **Domain changes reach the Proxy without a Deployment.** The Domains are
  The Bakery's to decide, not the Container's, so after an update that changes
  them projects publishes `ApplicationDomainsChanged` and routing moves the
  Route at once. A Deployment still passes them, so the first one creates the
  Route. Uniqueness across The Bakery stays here, where every Application's
  Domains are known (table `application_domains`, unique on the domain).
- **At most 10 Domains, the first is primary.** Enough for old names,
  `www` and apex, and a few aliases; one certificate each. A list is kept
  in order so "primary" needs no separate flag.
- **Removing a Persistent storage keeps its volume.** The volume is named
  after the Application id and the storage name, so re-adding the same name
  gets the data back, and a mistaken click cannot delete data. Only deleting
  the Application removes its volumes. Mount paths may not overlap in name
  only; nesting (`/data` and `/data/cache`) is the Owner's choice.
- **Resource limits are empty by default**, since a limit too low makes an
  app fail in ways that are hard to read; they take effect from the next
  Deployment (rollbacks included, which read today's settings).
- **Domains are shared with services through checks, not a shared table.**
  Services have Domains too, and the Proxy can serve a hostname only once.
  projects keeps `application_domains` (unique) and asks the Domain checks
  services registers; services asks `DomainInUse` before storing its own.
  Neither reads the other's tables. Cost: two creates racing in the two
  contexts could both win; with one Owner that is accepted.
- **The Target server is fixed once the Application exists.** Moving an
  Application to another Server means moving its Persistent storage and
  pointing its Domains' DNS elsewhere, which is a feature of its own. The
  Local server is stored as none (NULL), so no migration had to read the
  servers context's table to backfill existing Applications, and "local" has
  one representation.
- **Git repository, not Source.** In Coolify a Source is a GitHub App or a
  GitLab connection, and an Application's `git_repository` and
  `git_branch` are what it clones. The Bakery uses the same words so Source is
  free for that connection when it arrives. The Application tab that edits
  the Git repository is still labelled "Source", as Coolify's is.
- **Resource is an umbrella word, not an aggregate.** Coolify lists an
  Environment's Applications, Databases and Services together as its
  Resources; The Bakery does the same, but each kind stays owned by its own
  context (projects, databases, services), and nothing stores a Resource as
  such.
- **An Environment's page shows an Application's latest Deployment, not its
  container.** Coolify keeps a container status on every Application; The
  Bakery's Applications have none of their own, so the page shows the state
  of the latest Deployment (Finished, Failed, Building, …), as the
  Application page does. Databases and Services show their own status. The
  page has no Tags column or filter until Tags exist, and no description
  under a Resource's name, since Resources have none yet.
- **Generated names have 8 random characters, not 24.** Coolify names a
  Resource created without a name after its repository, image type or
  Database type plus a 24-character public id. The Bakery has no public ids
  yet and derives the Slug and the default Domain from the name, so 24
  characters would make both unreadable; 8 keeps them short and still makes
  a clash unlikely (and `freeSlug` resolves one if it happens). Databases and
  Services follow the same rule in their contexts.
- **The New Resource page shows only what The Bakery can create.** Coolify's
  chooser also offers Git repositories through a GitHub or GitLab App, a
  Dockerfile without a repository, KeyDB, Dragonfly and ClickHouse, a
  PostgreSQL image picker (Supabase, PostGIS, PGVector) and connecting an
  existing PostgreSQL; none exists here yet, so the cards are left out
  rather than shown dead. Valkey has a card Coolify does not. Destinations
  do not exist either, so there is no "Select a destination" step, and the
  "Select a server" step is asked only for Applications: Databases, Services
  and a pasted Docker Compose file (which becomes a Service) run on the
  Local server. A remote Server counts as ready once validated; the Local
  server always does. Cards link to the upstream projects' documentation
  (git, Podman, the database's own), not to Coolify's.
- **The create pages ask for less than Coolify's.** "Check repository" on
  the Public Git Repository page checks the URL only: The Bakery has no Git
  provider API to list branches, so the branch comes from a `/tree/<branch>`
  link or defaults to `main`. Its build packs are The Bakery's (Nixpacks,
  Static, Dockerfile); there is no Base directory, no Nixpacks output type
  and no Docker Compose build pack, since Applications have none of them.
  The Private Git Repository page does not ask for a Private Key: The Bakery
  generates a Deploy key per Application, which the Application page shows
  to add to the repository before the first deploy. The Docker Image page
  asks for the Port too, since the Proxy needs it before the first deploy.
  The Docker Compose page creates a Service (Coolify's "Docker Compose
  Empty"), and its compose file is checked as any Service's: a `build:` or
  `ports:` key is refused with its line.
- **The Project pages follow Coolify's, with numeric ids.** The dashboard's
  paths have Coolify's shape (`#/project/{id}`, `…/environment/{id}`,
  `…/new`, `…/edit`) but carry The Bakery's numeric ids, since Projects and
  Environments have no public ids (UUIDs) yet; the Coolify API at `/api/v1`
  will bring them. A Project has no icon, as nothing stores one, and an
  Environment has no "Clone" action: cloning copies Resources with their
  Persistent storage and Domains, a feature of its own across three
  contexts. Without Tags there is no Tags filter or column.
- **Shared variables live on the settings pages for now.** Coolify edits a
  Project's and an Environment's shared variables on separate Shared
  Variables pages; until those pages exist, Project settings and
  Environment settings hold them, so they stay reachable.
