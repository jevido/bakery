# projects

- Subdomain: supporting
- Hosted in: `services/api` (module `contexts/projects`)

## Purpose

Holds what the Owner wants to run: Projects, their Environments, the
Applications in them, each Application's Env vars, Health check, Domains, Persistent storage and Resource limits, and the
Shared variables of Projects and Environments. It is **not**
responsible for building or running anything (deployments) or for how traffic
reaches an Application (routing).

## Language

| Term | Meaning |
| ---- | ------- |
| Project | A named group of Environments. |
| Environment | A stage in a Project; `production` exists from the start. Names are unique per Project. |
| Application | A Build pack with what it needs (Source and Dockerfile path, Source and Publish directory, or Image reference and Registry credentials) + port + Domains, plus Env vars, a Health check, Persistent storage and Resource limits. |
| Build pack | `dockerfile`, `nixpacks`, `static` or `image`: how the Application becomes an Image. |
| Image reference | The full registry reference an `image` Application runs. |
| Registry credentials | Username and password/token an `image` Application pulls with. |
| Publish directory | The directory of the Source a `static` Application serves. |
| Variable scope | Build (a build arg) and/or runtime (the Container's environment). |
| Shared variable | A variable on a Project or Environment, inherited by its Applications. |
| Health check | Whether and how a new Container is probed before it takes traffic: path, interval, timeout, retries, start period. |
| Deploy key | The SSH key pair of one Application with an SSH Source. |
| Domain | One of the 1–10 hostnames of an Application; the first is its primary Domain. |
| Persistent storage | A name and a mount path; every Container of the Application mounts the volume of that name there. |
| Resource limits | Memory in MB and CPU in cores per Container; empty means unlimited. |
| Application snapshot | The read-only view of an Application handed to deployments, with its variables merged and decrypted into a build and a runtime set, and the Deploy key's private half decrypted. |

## Model

### Aggregates

| Aggregate | Invariants |
| --------- | ---------- |
| Project | Name is not empty. Is created together with its `production` Environment, in one transaction. Environment names are unique within the Project. Its Shared variables, and those of each of its Environments, follow the Env var rules below. |
| Application | Slug is unique across Bakery, lowercase `[a-z0-9-]`. The Build pack is `dockerfile` (default), `nixpacks`, `static` or `image`. An `image` Application has an Image reference that names its registry host (no short names like `nginx`, at most 500 characters, no spaces), and no Source, Dockerfile path or Deploy key; it may have Registry credentials, username and password both set or both empty, the password encrypted at rest and never returned. Every other Build pack has a Source and no Image reference or Registry credentials. A `static` Application has a Publish directory that is relative and does not contain `..`, and always listens on port 80. Source URL is either `https://` without credentials, or an SSH URL (`ssh://user@host[:port]/path` or `user@host:path`); never `file://`, `ext::`, a local path or anything starting with `-`. An SSH Source always has a Deploy key (ed25519, generated by Bakery); an `https://` Source has none. The Deploy key's private half is encrypted at rest and only leaves the context in the snapshot; it is never shown or logged. Branch is not empty. Dockerfile path is relative and does not contain `..`. Port is 1–65535. It has 1 to 10 Domains, in order (the first is primary), each a lowercase hostname, unique across Bakery (across every Application's Domains), not the dashboard domain (reserved for the Dashboard Route), listed once; an empty list becomes the one default Domain `<slug>.<domain suffix>`. At most 10 Persistent storages: names match `^[a-z0-9][a-z0-9-]{0,39}$` and are unique per Application; mount paths are absolute, already clean (`path.Clean` leaves them unchanged), not `/`, without `:` or `,`, at most 200 characters and unique per Application. Resource limits are optional: memory 16–65536 MB, CPU 0.1–64 cores with at most two decimals. Env var names match `^[A-Za-z_][A-Za-z0-9_]*$` and are unique per Application; values are encrypted at rest and never logged; each has at least one scope (build, runtime), runtime only by default. The Health check is off by default; its path starts with `/`, interval is 1–300 s, timeout 1–60 s, retries 1–100, start period 0–600 s. |

### Commands

- `CreateProject`, `RenameProject`, `DeleteProject` (refused while it has Applications).
- `CreateApplication(environment, ...)`, `UpdateApplication`, `DeleteApplication`.
- `ReplaceEnvVars(application, [name, value, build, runtime])`: the whole set is replaced at once.
- `ReplaceProjectVariables(project, ...)`, `ReplaceEnvironmentVariables(environment, ...)`: the same, for Shared variables.
- `RegenerateDeployKey(application)`: a new key pair replaces the old one; the Owner has to add the new public half to the repository.

### Domain events

- `ApplicationDeleted { applicationID }`: routing drops its Route and Route settings; deployments removes its Containers and volumes.
- `ApplicationDomainsChanged { applicationID, domains }`: fired after an update that changed the Domains (in their new order); routing points the Application's Route at them.

## Integration

- **Publishes:** `ApplicationForDeploy(id) (ApplicationSnapshot, error)` for
  deployments (Build pack, Source, Dockerfile path, Publish directory, Image reference and decrypted Registry credentials, port, Domains, Health check, Persistent storages, Resource limits,
  `BuildEnv` and `RuntimeEnv`, Deploy key). The two variable sets are
  already merged (Application > Environment > Project) and split by scope.
  Changing its fields is a breaking change for deployments.
  `ApplicationExists(id)` for routing, which keeps Route settings per
  Application and refuses them for one that does not exist.
- **Consumes:** the Owner's Session (identity middleware).

## Why it's shaped this way

- **Environments exist from day one**, even though only `production` is
  used. Coolify's Project > Environment > Resource shape is what later phases
  (previews, staging) need, and adding a level under existing Applications
  later would be a data migration.
- **The dashboard domain is reserved through configuration, not by asking
  routing.** Projects reads `BAKERY_DASHBOARD_DOMAIN` itself, so it needs no
  dependency on routing to refuse it; both contexts read the same setting.
- **Source URLs must be `https://`.** The deployment worker clones whatever
  URL it is given where the API runs (on the host in development, in the
  API container on a server); a `file://` URL or a local path would let an
  Application read the host's files. Private repositories are reached over
  SSH with a Deploy key instead, and an SSH Source without a key cannot
  exist, so Bakery never clones with a key of its own user.
- **Deploy keys first, a GitHub App later.** A deploy key works with every
  git host (GitHub, GitLab, Gitea, Forgejo) and needs nothing but the
  repository's settings page. A GitHub App needs a registration and a
  public callback, and becomes its own Source kind.
- **One Deploy key per Application**, not one per Bakery: GitHub refuses the
  same deploy key on a second repository, and a leaked key then opens only
  one repository.
- **Env var values are encrypted with the application key**
  (`APP_KEY`, AES via Goravel's Crypt). A database dump alone does not leak
  them. Cost: losing `APP_KEY` loses every value.
- **Shared variables are inherited, not referenced.** Coolify lets a value
  say `{{project.NAME}}`; Bakery simply hands every Application its
  Environment's and Project's variables, with the Application's own winning
  over its Environment's and those over its Project's. That covers the usual
  case (one `DATABASE_URL` per Environment) without a template language;
  references can be added on top later. A name overridden at a lower level
  takes that level's scope too, so the Owner sees one row per name.
- **The merge happens here, not in deployments.** Deployments gets two plain
  sets (`BuildEnv`, `RuntimeEnv`) and never learns that Projects and
  Environments have variables, so how variables are shared can change
  without touching it.
- **Build values end up in the Image's history.** Build args are visible to
  anyone who can inspect the Image, so runtime is the default scope and the
  dashboard warns when a variable is marked build.
- **Registry credentials belong to the Application**, not to a list of
  registries. It is the smallest thing that lets a private image deploy, and
  a leaked credential reaches one Application's image. A shared list per
  registry can come with Teams, when several people manage credentials.
- **Image references must name their registry.** On a server, rootless
  Podman resolves a short name like `nginx` through
  `unqualified-search-registries`, which differs per distribution and may
  prompt; `docker.io/library/nginx:1.27` means the same thing everywhere.
- **Nixpacks, not Railpack, for builds without a Dockerfile.** Railpack
  builds only through BuildKit (its plan is a BuildKit frontend), which
  Podman's builder (Buildah) cannot run, and running BuildKit would mean a
  second build daemon next to Podman. Nixpacks can write a plain Dockerfile
  that Podman builds. Nixpacks is in maintenance mode; if Railpack ever
  writes a Dockerfile it can replace it under the same Build pack name.
- **A static site has no build step yet** and always listens on port 80:
  the Publish directory is copied as is into a Caddy file server. A site
  that needs `npm run build` uses Nixpacks or a Dockerfile.
- **The Health check belongs to the Application**, since it describes the
  app (what path says it is ready), and deployments reads it from the
  snapshot like the port.
- **Domain changes reach the Proxy without a Deployment.** The Domains are
  Bakery's to decide, not the Container's, so after an update that changes
  them projects publishes `ApplicationDomainsChanged` and routing moves the
  Route at once. A Deployment still passes them, so the first one creates the
  Route. Uniqueness across Bakery stays here, where every Application's
  Domains are known (table `application_domains`, unique on the domain).
- **At most 10 Domains, the first is primary.** Enough for old names,
  `www` and apex, and a few aliases; one certificate each. A list is kept
  in order so "primary" needs no separate flag.
- **Removing a Persistent storage keeps its volume.** The volume is named
  after the Application id and the storage name, so re-adding the same name
  gets the data back, and a mistaken click cannot delete data. Only deleting
  the Application removes its volumes. Mount paths may not overlap in name
  only; nesting (`/data` and `/data/cache`) is the Owner's choice.
- **Resource limits are empty by default**, since a limit too low makes an
  app fail in ways that are hard to read; they take effect from the next
  Deployment (rollbacks included, which read today's settings).
